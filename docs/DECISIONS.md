덮어쓰지 않고 새로운 항목을 추가한다.

- 상태: 제안 | 확정 | 대체됨

## 결정 사항

### ADR-001: 제출 문서 없이 지원 기록 생성 허용

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 이력서나 자기소개서 업로드를 지원 기록 생성의 필수 조건으로 두면, 기존 지원 내역을 빠르게 등록하려는 사용자의 진입 장벽이 높아진다.
- 결정: 지원 기록은 제출 문서 없이도 생성할 수 있다. 이력서와 자기소개서 버전 연결은 선택 사항이며 나중에 추가할 수 있다.
- 영향: 지원 기록의 제출 문서 필드는 비어 있을 수 있어야 한다. 문서 버전별 통계에서는 문서가 연결되지 않은 지원 기록을 별도로 처리해야 한다.

### ADR-002: MVP 자기소개서는 파일과 버전 중심으로 관리

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 이력서뿐 아니라 기업별 자기소개서도 제출 버전 추적이 필요하지만, 초기부터 편집기와 문항별 답변 재사용 기능을 구현하면 MVP가 복잡해진다.
- 결정: MVP에서는 자기소개서 파일 업로드, 버전 관리, 지원 기록 연결을 제공한다. 이력서와 자기소개서는 독립적으로 관리하며 하나로 합쳐진 문서도 허용한다.
- 영향: 자기소개서 직접 작성, 문항별 답변 저장 및 재사용, 버전 간 내용 비교와 첨삭 기능은 후속 단계로 미룬다.

### ADR-003: 지원 상태는 기본값이 있는 필수 데이터로 관리

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 현재 지원 상태가 없으면 지원 현황과 단계별 통계를 일관되게 계산할 수 없지만, 매번 상태를 선택하게 하면 입력 부담이 늘어난다.
- 결정: 지원 상태는 현재 단계, 전체 결과와 필요한 경우 종료 사유로 분리해 저장한다. 현재 단계는 `서류`, `테스트/과제`, `면접`, `처우 협의`로 구성하고, 전체 결과는 `진행 중`, `최종 합격`, `입사 확정`, `불합격`, `종료`로 구성한다. 종료 사유는 `지원 철회`, `응답 없음`, `채용 취소`, `기타`로 구성한다. 새 지원의 기본값은 `서류`와 `진행 중`이며 `지원 완료` 최초 이벤트를 생성하고 화면에도 `지원 완료`로 표시한다.
- 영향: 화면에서는 값을 조합한 하나의 상태만 보여줘 입력 부담을 낮춘다. 불합격 및 종료 시 당시 단계를 보존할 수 있어 단계별 전환율과 합격률을 계산할 수 있다. 지원 전 관심 공고는 지원 기록과 분리해 통계에서 제외한다.

### ADR-004: 취업 데이터의 연결 관계를 시각화

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 일반적인 취업 관리 템플릿은 표, 보드, 캘린더 중심이어서 제출 문서와 지원 결과 사이의 전체 관계를 파악하기 어렵다.
- 결정: 이력서, 자기소개서, 기업, 지원 기록, 전형 단계와 결과의 연결을 자동으로 구성하고 탐색 가능한 시각화로 제공하는 것을 제품 방향으로 삼는다.
- 영향: 데이터 모델은 각 항목의 관계와 이력을 보존해야 한다. 전체 인터랙티브 그래프의 MVP 포함 범위와 UX는 별도로 검증하며, 개인 데이터 시각화는 기본 비공개로 제공한다.

### ADR-005: 동의 기반 이메일 연동 결과 자동 반영

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 채용 결과 메일을 자동으로 반영하면 기록 부담을 크게 줄일 수 있지만, 메일 분류나 지원 기록 매칭이 잘못되면 중요한 전형 상태가 부정확하게 변경될 수 있다.
- 결정: 이메일 연동은 MVP 이후에 구현한다. 사용자가 명시적으로 동의하면 신뢰도 높은 분석 결과를 지원 기록에 자동 반영한다. 매칭이 모호하거나 사용자가 자동 반영에 동의하지 않은 경우에는 변경만 제안한다.
- 영향: 모든 자동 변경은 근거 메일과 변경 내용을 알리고 되돌릴 수 있어야 한다. 연동은 최소 권한과 최소 데이터 저장 원칙을 따르며, OAuth 검증, 개인정보 처리, 연동 해제 및 데이터 삭제 기능을 함께 설계해야 한다.

### ADR-006: 면접 일정에 맞춰 AI 준비 자료 제공

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 사용자가 면접 일정을 등록한 뒤 기업, 직무, 채용공고와 제출 문서를 다시 찾아 분석하는 데 많은 시간이 든다.
- 결정: MVP 이후 면접 일정이 등록되거나 이메일에서 감지되면 해당 지원 기록과 연결된 정보를 바탕으로 기업·직무 분석, 예상 질문 및 준비 체크리스트를 자동 생성한다.
- 영향: 기업 정보에는 출처와 확인 날짜를 표시하고 확인되지 않은 내용을 사실처럼 제공하지 않는다. 이력서와 자기소개서를 AI 분석에 사용할 때는 별도 동의와 명확한 데이터 처리 안내가 필요하다.

### ADR-007: 제출 문서를 문서와 버전으로 분리

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 같은 이력서를 수정한 파일과 목표 직무나 강조 방향이 완전히 다른 이력서를 하나의 버전 목록으로 관리하면 변경 이력과 지원 연결이 불명확해진다.
- 결정: 이력서와 자기소개서는 독립된 문서 단위로 만들고 각 문서 안에 여러 버전을 둔다. 새 파일 등록 시 사용자가 `새 문서` 또는 `기존 문서의 새 버전`을 선택하며, 지원 기록은 특정 버전에 연결한다.
- 영향: 서비스는 문서 간 구분을 강제하지 않는다. 제출 기록에 연결된 버전은 수정하거나 덮어쓰지 않아 과거 제출 내용을 보존한다.

### ADR-008: 버전 비교 기능을 단계적으로 제공

- 날짜: 2026-10-16
- 상태: 확정
- 배경: PDF는 레이아웃, 다단 구성, 이미지 및 스캔 여부에 따라 자동 텍스트 비교의 정확도가 달라질 수 있다.
- 결정: MVP에서는 사용자가 버전별 변경 내용을 기록하고 선택한 두 PDF를 나란히 볼 수 있게 한다. PDF 텍스트 자동 추출, Git 스타일 추가·수정·삭제 비교와 AI 변경 요약은 후속 단계에서 개발한다.
- 영향: 버전은 변경 불가능한 원본 파일을 유지해야 한다. 후속 자동 비교를 위해 추출 텍스트, 처리 상태 및 비교 결과를 저장할 수 있는 구조를 고려하되 구체적인 구현 방식은 기술 설계 단계에서 결정한다.

### ADR-009: 원본 파일 삭제와 지원 이력 보존을 분리

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 제출 문서의 과거 버전을 보존해야 지원 이력이 정확하게 유지되지만, 민감한 개인정보가 포함된 원본 파일을 사용자가 삭제하지 못하게 해서는 안 된다.
- 결정: 제출된 버전은 덮어쓰지 않되 사용자가 언제든 원본 파일 또는 버전 전체를 삭제할 수 있게 한다. 원본만 삭제하면 파일과 파생 데이터를 파기하고 지원 이력에 필요한 최소 메타데이터만 유지한다.
- 영향: 파일 삭제, 버전 삭제, 지원 기록 삭제 및 계정 탈퇴를 구분해 연쇄 삭제 범위를 설계해야 한다. 파일은 비공개 저장소와 짧은 유효기간의 접근 링크를 사용하며, 구체적인 저장 업체와 백업 파기 기한은 기술 설계 및 개인정보처리방침 작성 시 확정한다.

### ADR-010: 응답 없음을 별도 결과로 보존하고 실질 성과에 반영

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 결과가 오지 않는 지원은 구직자 관점에서 실질적인 실패이지만, 기업이 명시적으로 불합격 처리한 사실과 동일하게 저장하면 결과 데이터가 왜곡된다.
- 결정: 응답 없음은 불합격과 별도의 종료 사유로 저장한다. 확정 합격률에서는 제외하고 전체 지원 기준 단계 전환율에서는 실질적 실패로 포함하며, 미응답률을 별도로 제공한다.
- 영향: 진행 중인 지원에 30일 동안 새 기록이 없으면 응답 없음 종료를 제안하지만 자동 변경하지 않는다. 늦게 결과가 도착하면 종료된 지원을 다시 열 수 있어야 한다.

### ADR-011: 지원별 여러 일정과 하나의 다음 할 일 제공

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 하나의 지원에는 테스트, 과제, 여러 차례의 면접과 후속 연락 등 복수 일정이 발생하지만 모든 일정을 한꺼번에 강조하면 화면이 복잡해진다.
- 결정: 지원 기록마다 여러 일정과 할 일을 등록할 수 있게 하고, 가장 가까운 미완료 항목 하나를 `다음 할 일`로 강조한다. MVP에서는 등록, 완료, 기한 초과 표시와 대시보드 조회를 제공한다.
- 영향: 일정은 종류, 제목, 날짜와 시간, 완료 여부 및 메모를 저장한다. 이메일 자동 등록, 외부 캘린더 연동과 별도 알림 발송은 후속 단계로 미룬다.

### ADR-012: MVP 제출 문서는 PDF만 지원

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 여러 파일 형식을 지원하면 형식별 미리보기, 비교, 보안 검사와 변환 처리가 필요해 MVP가 복잡해진다.
- 결정: MVP에서는 이력서, 자기소개서 및 통합 문서를 PDF로만 업로드할 수 있게 하고 파일당 최대 크기를 10MB로 제한한다. 암호화된 PDF는 업로드를 제한하고 해제 방법을 안내한다.
- 영향: 확장자가 아니라 실제 파일 형식을 검사해야 한다. DOCX와 HWP/HWPX 지원은 후속 단계로 미루며, 사용자별 전체 저장 용량은 기술 스택과 운영비를 검토한 뒤 확정한다.

### ADR-013: 지원 상태 변경을 이벤트 이력으로 보존

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 상태를 덮어쓰면 전형 과정과 단계별 소요 시간을 알 수 없고, 이메일 자동화나 사용자의 실수를 안전하게 복구할 수 없다.
- 결정: 상태 변경마다 시각, 이전 값, 변경된 값과 변경 주체를 이벤트로 추가한다. 자동 및 수동 상태 변경은 되돌릴 수 있으며 되돌리기도 새로운 이벤트로 기록한다.
- 영향: 현재 상태는 이벤트 이력과 일관되게 유지해야 한다. 불필요한 메일 본문 등 민감정보는 이력에 저장하지 않고, 복구할 수 없는 영구 삭제에는 별도 확인 절차를 적용한다.

### ADR-014: 데이터 내보내기는 MVP 이후에 제공

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 데이터 내보내기는 사용자 소유권과 신뢰에 중요하지만 문서 등록, 지원 관리와 통계라는 MVP 핵심 흐름을 검증하는 데 필수적이지 않다.
- 결정: MVP에서는 내보내기를 제외한다. 후속 단계에서 지원 기록 CSV를 먼저 제공하고, 상태 이력과 일정, 원본 PDF를 포함한 전체 백업으로 확장한다.
- 영향: 초기 데이터 모델부터 사용자별 소유 관계와 구조화된 기록을 명확히 유지해 향후 안전하게 내보낼 수 있어야 한다.

### ADR-015: AI 취업 활동 인사이트는 통계 근거와 한계를 함께 제시

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 지원 통계와 제출 문서별 결과를 AI가 해석하면 사용자가 강점과 개선 지점을 찾는 데 도움이 되지만, 표본이 적거나 기업과 직무 조건이 다른 데이터를 과도하게 일반화하면 잘못된 판단을 유도할 수 있다.
- 결정: AI 취업 활동 인사이트는 MVP 이후에 제공한다. 분석 기간, 표본 수와 근거 지표를 함께 표시하고 데이터가 부족하면 평가를 생성하지 않는다. 문서 버전과 결과의 관계는 상관관계로만 설명하며 특정 이력서가 결과의 원인이라고 단정하지 않는다. 기본 통계는 AI 없이 재현 가능한 계산 규칙으로 산출한다.
- 영향: AI 응답 형식에 근거 지표와 불확실성 표현이 포함되어야 하며 품질 평가 기준이 필요하다. 이력서나 자기소개서 본문을 분석할 때는 별도 동의와 개인정보 처리 안내가 필요하다.

### ADR-016: Next.js App Router를 풀스택 애플리케이션으로 사용

- 날짜: 2026-10-16
- 상태: 확정
- 배경: MVP에서 프론트엔드와 별도 백엔드를 함께 운영하면 인증, 타입 공유, 배포와 오류 처리의 복잡도가 증가한다.
- 결정: Next.js App Router를 화면과 서버 기능을 함께 담당하는 풀스택 프레임워크로 사용하고 Node.js 런타임에서 실행한다. MVP에서는 Express 또는 NestJS 기반의 별도 백엔드 서버를 두지 않는다.
- 영향: 하나의 TypeScript 저장소에서 핵심 기능을 빠르게 구현할 수 있다. 장시간 실행, 재시도 또는 독립 확장이 필요한 AI, 이메일 및 OCR 작업은 필요성이 확인되면 별도 Node.js Worker로 분리한다.

### ADR-017: Supabase에서 PostgreSQL, Auth와 Storage를 사용

- 결정: Supabase PostgreSQL을 주 데이터베이스로, Supabase Auth를 인증 서비스로, Supabase Storage를 비공개 PDF 저장소로 사용한다.
- 영향: 초기에는 하나의 서비스에서 핵심 인프라를 관리할 수 있다. 무료 플랜의 용량, 일시 중지와 백업 제한을 고려해야 하며 로그인 제공 방식, 리전, 백업 및 이전 정책은 별도로 결정한다.

### ADR-018: Drizzle로 데이터 스키마와 마이그레이션을 관리

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 지원 기록, 상태 이벤트, 일정과 문서 버전처럼 관계가 많은 데이터를 타입 안전하게 다루고 데이터베이스 변경 이력을 코드와 함께 관리할 필요가 있다.
- 결정: Next.js 서버에서 Drizzle ORM으로 Supabase PostgreSQL에 접근하고 Drizzle Kit으로 SQL 마이그레이션을 생성한다. 스키마와 마이그레이션은 Git에 포함하며 Drizzle을 브라우저에서 사용하지 않는다.
- 영향: TypeScript 타입과 SQL에 가까운 쿼리를 사용할 수 있다. 직접 데이터베이스 연결은 사용하는 역할에 따라 Supabase RLS를 우회할 수 있으므로 서버의 인증 및 소유권 검사와 권한 테스트를 필수로 하고 RLS 적용 방식은 인증 설계에서 확정한다.

### ADR-019: MVP는 Google과 Kakao 소셜 로그인만 제공

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 비밀번호 기반 계정 관리 부담을 줄이면서 국내 사용자가 익숙한 로그인 경험을 제공해야 한다. Google, Kakao와 Naver를 한 번에 구현하면 Naver Custom OAuth 검증과 계정 연결 정책으로 MVP 인증 범위가 커진다.
- 결정: Supabase Auth를 통해 Google과 Kakao 소셜 로그인을 MVP에 제공한다. 이메일·비밀번호와 매직 링크 로그인은 제공하지 않으며 Naver 로그인은 MVP 이후 Custom OAuth 호환성을 검증한 뒤 추가한다. 로그인 권한과 Gmail 채용 메일 분석 권한은 분리한다.
- 영향: 비밀번호 재설정 기능은 필요하지 않지만 OAuth 제공자 설정, 콜백 URL과 세션 처리가 필요하다. 같은 사용자가 서로 다른 제공자로 로그인할 때 발생하는 계정 연결 및 중복 처리 정책은 구현 전에 별도로 확정해야 한다.

### ADR-020: 모든 사용자 데이터에 소유자 ID를 저장

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 하위 데이터가 부모 관계로만 소유자를 추론하면 매번 조인이 필요하고 권한 필터를 빠뜨릴 위험이 커진다. MILO의 지원 기록과 제출 문서는 민감한 개인 데이터이므로 소유권 검사가 단순하고 명확해야 한다.
- 결정: 사용자 데이터 테이블마다 `user_id`를 직접 저장한다. 하위 테이블은 `(parent_id, user_id)` 복합 외래 키로 부모와 동일한 사용자에게 속함을 데이터베이스에서 강제한다.
- 영향: 소유자 정보가 중복되지만 서버 쿼리와 RLS 정책이 단순해진다. 생성과 연결 시 `user_id` 일관성을 유지해야 하며 권한 테스트에서 다른 사용자의 ID 조합을 거부하는지 검증한다.

### ADR-021: 현재 상태와 추가 전용 이벤트 이력을 함께 유지

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 이벤트만 재생해 현재 상태를 계산하면 조회와 구현이 복잡해지고, 현재 상태만 저장하면 전형 과정과 되돌리기 이력을 잃는다.
- 결정: `applications`에 현재 단계, 전체 결과와 종료 사유를 저장하고 `application_events`에 모든 상태 변화를 추가 전용으로 기록한다. 두 데이터는 하나의 트랜잭션에서 변경하며 되돌리기도 대상 이벤트를 참조하는 새 이벤트로 추가한다.
- 영향: 목록 조회와 통계 계산이 단순해지지만 현재 상태와 마지막 이벤트가 불일치하지 않도록 트랜잭션과 불변조건 테스트가 필요하다.

### ADR-022: 개인 데이터는 기본 거부하고 명시적 공유만 허용

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 사용자가 원하면 이력서를 피드백이나 커뮤니티 목적으로 공유할 수 있어야 하지만, 이력서 공유가 기업 지원 내역과 다른 개인정보 노출로 확장되어서는 안 된다.
- 결정: 모든 개인 데이터 접근은 기본적으로 소유자만 허용한다. MVP에는 공유 기능을 제공하지 않는다. 후속 공유 기능에서는 소유자가 선택한 특정 자원, 대상과 허용 동작에 대한 활성 권한이 있을 때만 접근을 허용하고 언제든 철회할 수 있게 한다.
- 영향: 문서 조회, 댓글과 첨삭 권한을 분리하고 기업 지원 기록, 결과, 통계와 메모는 별도 허용 없이는 공개하지 않는다. 철회 후 새로운 접근과 임시 링크 발급은 막을 수 있지만 이미 내려받은 파일은 회수할 수 없으므로 공유 전에 안내해야 한다.

### ADR-023: 일정은 날짜 필수, 시간 선택으로 저장

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 면접처럼 정확한 시각이 있는 일정과 결과 발표 예정처럼 날짜만 아는 일정이 함께 존재한다. 임의의 시간을 강제하면 사용자가 알지 못하는 정보를 입력하거나 잘못된 기한 초과 알림이 발생할 수 있다.
- 결정: 일정은 `scheduled_on` 날짜를 필수로, `scheduled_time` 시간을 선택으로 저장하고 생성 당시의 IANA 시간대를 함께 보존한다. 시간이 있는 일정은 정확한 시각 이후, 날짜만 있는 일정은 해당 시간대에서 그날이 끝난 이후 기한 초과로 처리한다.
- 영향: 입력 장벽을 낮추면서 정확한 면접 시각을 보존할 수 있다. 다음 할 일 정렬과 기한 초과 계산은 날짜, 선택 시간과 저장된 시간대를 함께 고려해야 하며 프로필 시간대 변경이 기존 일정에 영향을 주지 않아야 한다.

### ADR-024: Tailwind CSS와 shadcn/ui를 기본 UI 구성으로 사용

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 반응형 화면과 접근 가능한 공통 컴포넌트를 빠르게 구축하면서도 서비스의 디자인과 컴포넌트 코드를 직접 관리할 필요가 있다.
- 결정: Tailwind CSS로 스타일과 디자인 토큰을 관리하고 shadcn/ui를 접근 가능한 UI 컴포넌트 기반으로 사용한다. 가져온 컴포넌트는 MILO의 요구사항과 디자인에 맞게 프로젝트 내부에서 관리한다.
- 영향: 초기 UI 구현 속도와 일관성을 확보할 수 있지만 클래스와 컴포넌트 변형이 무질서하게 늘지 않도록 공통 토큰과 재사용 경계를 관리해야 한다. TanStack Query와 Zustand는 실제 상태 관리 필요가 확인되기 전까지 설치하지 않는다.

### ADR-025: 라이트 테마와 의미 기반 디자인 토큰을 우선 적용

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 브랜드의 기본 인상은 화이트 배경과 연한 연두색이며, MVP 개발 단계에서 라이트·다크 테마를 동시에 완성하면 디자인 검토와 구현 범위가 늘어난다. 다만 컴포넌트에 색상 값을 직접 사용하면 추후 다크 모드 확장이 어려워진다.
- 결정: MVP는 화이트 배경의 라이트 테마만 제공하고 Milo Lime `#9DDF50`을 브랜드 중심 색상으로 사용한다. Tailwind CSS에서는 역할을 나타내는 CSS 변수와 디자인 토큰을 사용하며 컴포넌트에 원시 색상 값을 반복하지 않는다. 다크 모드는 후속 단계에서 토큰 값을 확장해 제공한다.
- 영향: 초기 디자인과 테스트 범위를 줄이면서 추후 테마 확장 경로를 유지할 수 있다. 연한 브랜드 색상 위 텍스트와 아이콘은 접근성 대비를 충족하도록 어두운 전경색을 사용한다.

### ADR-026: 초기 로고는 단순한 도로 방패와 M 심볼을 사용

- 날짜: 2026-10-16
- 상태: 확정
- 배경: 프로젝트 초기에는 작은 크기에서도 구분되는 브랜드 표시가 필요하지만 완성형 브랜딩에 많은 시간을 쓰는 것은 MVP 구현을 늦출 수 있다.
- 결정: Milo Lime 도로 방패 안에 굵은 `M`을 배치한 단순한 SVG 심볼을 초기 로고로 사용한다. 실제 미국 도로 표지판을 그대로 복제하지 않고 형태를 단순화하며, 별도 장식과 작은 문구는 넣지 않는다.
- 영향: 파비콘, 내비게이션과 로그인 화면에서 일관된 임시 브랜드 표시를 사용할 수 있다. 로고 파일과 사용 위치를 분리해 향후 워드마크나 완성형 심볼로 교체하기 쉽게 유지한다.
